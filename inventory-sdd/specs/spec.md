# Spec: ฟีเจอร์แจ้งเตือนสต็อกต่ำ และรายงานมูลค่าสต็อก (v2 — Revised)

> **หมายเหตุ:** เอกสารนี้แก้ไขจากฉบับร่างเดิม ตามผลรีวิว spec ครั้งก่อน — จุดที่แก้ไขจะมีเครื่องหมาย 🔧 กำกับไว้ พร้อมสรุปเหตุผลสั้น ๆ

---

## 1. เป้าหมาย (Goal)
เพิ่มความสามารถให้ระบบ inventory แจ้งเตือนผู้จัดการเมื่อสินค้าใดต่ำกว่าหรือเท่ากับ threshold
และให้ผู้จัดการดูรายงานมูลค่าสต็อกแยกตามหมวดหมู่ได้ พร้อมทั้งส่งออกข้อมูลสินค้าและรายงานเป็นไฟล์ CSV

## 2. User Story
| รหัส | User Story |
|---|---|
| US-01 | ในฐานะพนักงาน ฉันต้องการดูรายการสินค้าทั้งหมดพร้อมจำนวนคงเหลือ เพื่อให้สามารถตรวจเช็กสต็อกได้อย่างรวดเร็ว |
| US-02 | ในฐานะพนักงาน ฉันต้องการเพิ่มสินค้าใหม่เข้าระบบ เพื่อให้ข้อมูลสต็อกมีความครบถ้วนและเป็นปัจจุบันเสมอ |
| US-03 | ในฐานะพนักงาน ฉันต้องการปรับปรุงจำนวนสต็อกเมื่อมีการรับเข้าหรือจ่ายออก เพื่อให้ยอดสินค้าคงเหลือถูกต้องตรงกับความเป็นจริง และได้รับแจ้งเตือนเมื่อสต็อกใกล้หมด |
| US-04 | ในฐานะผู้จัดการ ฉันต้องการค้นหาสินค้าด้วยชื่อหรือรหัสสินค้า เพื่อดูรายละเอียดได้อย่างรวดเร็ว |
| US-05 | ในฐานะผู้จัดการ ฉันต้องการส่งออกรายการสินค้าทั้งหมด (หรือเฉพาะที่กรองแล้ว) เป็นไฟล์ CSV เพื่อนำข้อมูลไปใช้งานต่อในระบบบัญชี |
| US-06 🔧 | ในฐานะผู้จัดการ ฉันต้องการดูรายงานสรุปมูลค่าสต็อกคงเหลือแยกตามหมวดหมู่ เพื่อประเมินมูลค่าทรัพย์สินคงคลัง |

> 🔧 **เพิ่ม US-06** เพราะ Goal และ FR-08 พูดถึง "รายงานมูลค่าสต็อก" แต่ฉบับเดิมไม่มี User Story รองรับ (traceability gap)

## 3. Acceptance Criteria (Given-When-Then)

### AC-01 (US-03 / FR-05, FR-06) — จ่ายสินค้าจนสต็อก ≤ threshold 🔧
```gherkin
Scenario: จ่ายสินค้าจนสต็อกต่ำกว่าหรือเท่ากับ threshold
  Given สินค้า "SKU-WIRE-01" มีสต็อก 20 หน่วย และ threshold = 15
  When พนักงานบันทึกจ่ายออก 8 หน่วย
  Then สต็อกคงเหลือ 12 หน่วย
  And ระบบยิง SMS-style notification (ยืนยันการทำรายการ) เสมอ
  And ระบบยิง Email-style low-stock notification เพิ่ม เนื่องจาก 12 <= 15
  And ทั้งสอง notification ปรากฏแยกกันบน console log

Scenario: จ่ายสินค้าจนสต็อกเท่ากับ threshold พอดี (boundary case)
  Given สินค้า "SKU-WIRE-01" มีสต็อก 20 หน่วย และ threshold = 15
  When พนักงานบันทึกจ่ายออก 5 หน่วย
  Then สต็อกคงเหลือ 15 หน่วย
  And ระบบต้องยิง low-stock notification (เกณฑ์คือ quantity <= threshold)

Scenario: จ่ายสินค้าโดยสต็อกยังสูงกว่า threshold
  Given สินค้า "SKU-WIRE-01" มีสต็อก 50 หน่วย และ threshold = 15
  When พนักงานบันทึกจ่ายออก 10 หน่วย
  Then สต็อกคงเหลือ 40 หน่วย
  And ระบบยิงเฉพาะ SMS-style notification ยืนยันการทำรายการ
  And ระบบไม่ยิง low-stock notification
```
> 🔧 เปลี่ยนเกณฑ์เป็น `quantity <= threshold` (เดิมกำกวมระหว่าง `<` กับ `<=`) และระบุชัดว่ากรณี low-stock จะมี **2 notification พร้อมกัน** (SMS ยืนยันธุรกรรม + Email แจ้งสต็อกต่ำ) ไม่ใช่แค่ 1 อย่างที่ฉบับเดิมกำกวม

### AC-02 (US-01 / FR-01) — แสดงรายการสินค้าและจำนวนคงเหลือ
```gherkin
Scenario: แสดงรายการสินค้าและจำนวนคงเหลือสำเร็จ (Happy Path)
  Given พนักงานเปิดหน้า "จัดการคลังสินค้า" และมีสินค้าอยู่ในระบบอย่างน้อย 1 รายการ
  When ระบบโหลดข้อมูลเสร็จสิ้น
  Then พนักงานต้องเห็นตารางรายการสินค้าที่มีข้อมูล SKU, ชื่อสินค้า, หมวดหมู่, จำนวนคงเหลือ ครบทุกแถว
  And แถวของสินค้าที่ quantity <= threshold ต้องมี CSS class "low-stock" (พื้นหลังสีแดง #FCE8E8) กำกับ 🔧

Scenario: แสดงรายการเมื่อไม่มีสินค้าในระบบเลย (Empty State) 🔧
  Given ไม่มีสินค้าใด ๆ ในระบบ
  When พนักงานเปิดหน้า "จัดการคลังสินค้า"
  Then ระบบแสดงข้อความ "ยังไม่มีสินค้าในระบบ" แทนตารางเปล่า
```
> 🔧 เปลี่ยนจาก "แสดงสีไฮไลต์ (เช่น สีแดง/ส้ม) หรือสัญลักษณ์เตือน" ที่กำกวม → ระบุ CSS class และค่าสีที่แน่นอนเพื่อให้ testable และเพิ่มเคส empty state ที่ขาดไป

### AC-03 (US-02 / FR-02) — เพิ่มสินค้าใหม่
```gherkin
Scenario: บันทึกข้อมูลสินค้าใหม่สำเร็จ (Happy Path)
  Given พนักงานเปิดฟอร์ม "เพิ่มสินค้าใหม่"
  When พนักงานกรอกข้อมูลครบถ้วน (SKU ไม่ซ้ำ, ชื่อ, หมวดหมู่, ราคาทุน > 0, ราคาขาย > 0, หน่วยนับ, จำนวนตั้งต้น >= 0, threshold >= 0) แล้วกดปุ่ม "บันทึก"
  Then ระบบบันทึกข้อมูลสำเร็จ แสดงข้อความ "เพิ่มสินค้าเรียบร้อยแล้ว" และแสดงสินค้านั้นในหน้ารายการสินค้าทันที

Scenario: ระบบปฏิเสธการเพิ่มสินค้าเมื่อใช้รหัสซ้ำ (Duplicate SKU, case-insensitive) 🔧
  Given ในระบบมีสินค้ารหัส "SKU-999" อยู่แล้ว
  When พนักงานกรอกแบบฟอร์มโดยใช้รหัสสินค้า "sku-999" (ตัวพิมพ์เล็ก) แล้วกดปุ่ม "บันทึก"
  Then ระบบต้องไม่อนุญาตให้บันทึก และแสดงข้อความ "รหัสสินค้านี้มีอยู่ในระบบแล้ว"
  # การเทียบ SKU ถือเป็น case-insensitive เสมอ

Scenario: ระบบปฏิเสธเมื่อราคาหรือจำนวนตั้งต้นเป็นค่าติดลบ 🔧
  Given พนักงานเปิดฟอร์ม "เพิ่มสินค้าใหม่"
  When พนักงานกรอกราคาทุน = -10 หรือจำนวนตั้งต้น = -5
  Then ระบบต้องไม่อนุญาตให้บันทึก และแสดงข้อความ "ค่าต้องไม่ติดลบ"

Scenario: ระบบปฏิเสธเมื่อไม่ระบุ threshold 🔧
  Given พนักงานเปิดฟอร์ม "เพิ่มสินค้าใหม่" และเว้นช่อง threshold ว่างไว้
  When พนักงานกดปุ่ม "บันทึก"
  Then ระบบต้องไม่อนุญาตให้บันทึก และแสดงข้อความ "กรุณาระบุ threshold"
```
> 🔧 เพิ่ม `threshold` เข้าไปเป็น required field (เดิมหายไปทั้งที่ schema กำหนดว่าต้องมี), แยก `ราคา` เป็น `ราคาทุน`/`ราคาขาย` ให้ตรงกับ schema, เพิ่ม validation สำหรับค่าติดลบ และระบุว่า SKU dedup เป็น case-insensitive

### AC-04 (US-03 / FR-03, FR-04) — รับเข้า / ตัดจ่าย
```gherkin
Scenario: ปรับเพิ่มยอดจากการรับสินค้าเข้าสำเร็จ (Stock-in)
  Given สินค้า "B-100" มียอดคงเหลือ 20 หน่วย
  When พนักงานเลือกทำรายการ "รับเข้า" จำนวน 10 หน่วย ระบุหมายเหตุ และกดยืนยัน
  Then ยอดคงเหลือของ "B-100" ต้องอัปเดตเป็น 30 หน่วย พร้อมบันทึกประวัติลง Audit Log

Scenario: ปฏิเสธการตัดจ่ายเมื่อยอดสินค้าไม่เพียงพอ
  Given สินค้า "B-100" มียอดคงเหลือ 5 หน่วย
  When พนักงานเลือกทำรายการ "เบิกจ่าย" จำนวน 10 หน่วย
  Then ระบบต้องไม่อนุญาตให้ทำรายการ และแสดงข้อความ "จำนวนคงเหลือไม่เพียงพอสำหรับการตัดจ่าย"

Scenario: ตัดจ่ายเท่ากับยอดคงเหลือพอดี (boundary case) 🔧
  Given สินค้า "B-100" มียอดคงเหลือ 5 หน่วย
  When พนักงานเลือกทำรายการ "เบิกจ่าย" จำนวน 5 หน่วย
  Then ระบบอนุญาตให้ทำรายการ และยอดคงเหลือของ "B-100" ต้องอัปเดตเป็น 0 หน่วย

Scenario: ปฏิเสธเมื่อกรอกจำนวนเป็น 0 หรือค่าที่ไม่ใช่ตัวเลข 🔧
  Given สินค้า "B-100" มียอดคงเหลือ 20 หน่วย
  When พนักงานเลือกทำรายการ "รับเข้า" จำนวน 0 หรือกรอกข้อความที่ไม่ใช่ตัวเลข
  Then ระบบต้องไม่อนุญาตให้ทำรายการ และแสดงข้อความ "จำนวนต้องเป็นตัวเลขที่มากกว่า 0"
```
> 🔧 เพิ่ม boundary case (เบิกพอดีเท่ายอดคงเหลือ → เหลือ 0) และเคส invalid input (0 / non-numeric) ที่ขาดไปจากฉบับเดิม

### AC-05 (US-04 / FR-07) — ค้นหาสินค้า
```gherkin
Scenario: ค้นหาด้วยคำบางส่วนแล้วพบข้อมูล (Partial Match, case-insensitive)
  Given มีสินค้าชื่อ "สมุดบันทึกริมลวด A5" ในระบบ และระบบมีสินค้าทั้งหมดไม่เกิน 1,000 รายการ 🔧
  When ผู้จัดการพิมพ์คำว่า "ริมลวด" ในช่องค้นหา
  Then ระบบต้องแสดงรายการ "สมุดบันทึกริมลวด A5" บนหน้าจอภายในเวลาไม่เกิน 0.5 วินาที 🔧

Scenario: ค้นหาแล้วไม่พบข้อมูล (No Data Found)
  Given ไม่มีสินค้าที่ตรงกับคำค้นหาในระบบ
  When ผู้จัดการพิมพ์คำว่า "XYZ99999" ในช่องค้นหา
  Then ระบบต้องแสดงข้อความ "ไม่พบข้อมูลสินค้าที่ค้นหา"

Scenario: ค้นหาด้วยช่องว่างเปล่า 🔧
  Given ผู้จัดการอยู่ในหน้าค้นหา
  When ผู้จัดการไม่กรอกคำค้นหาใด ๆ (string ว่าง)
  Then ระบบแสดงรายการสินค้าทั้งหมด (เทียบเท่ากับไม่มีการกรอง)
```
> 🔧 รวมเกณฑ์เวลาให้ตรงกับ NFR-01 (0.5s) แทนที่จะมีมาตรฐานแยก 2 วินาที ระบุขนาด dataset ที่ทดสอบ และเพิ่มเคส search ว่างเปล่า

### AC-06 (US-05 / FR-09) — Export CSV รายการสินค้า
```gherkin
Scenario: ส่งออกข้อมูลสินค้าทั้งหมดเป็นไฟล์ CSV สำเร็จ (Export All)
  Given ผู้จัดการอยู่ในหน้ารายการสินค้า และมีสินค้าอย่างน้อย 1 รายการ
  When ผู้จัดการกดปุ่ม "Export CSV" โดยไม่ได้เลือกตัวกรองใดๆ
  Then ระบบดาวน์โหลดไฟล์ .csv (UTF-8 with BOM) ที่มีข้อมูลสินค้าทั้งหมด แสดงผลภาษาไทยถูกต้องสมบูรณ์

Scenario: ส่งออกเฉพาะข้อมูลที่ผ่านการกรอง (Export Filtered Results)
  Given ผู้จัดการค้นหาหมวดหมู่ "เครื่องเขียน" และระบบแสดงผลเฉพาะสินค้าในหมวดหมู่นี้
  When ผู้จัดการกดปุ่ม "Export CSV"
  Then ไฟล์ CSV ที่ดาวน์โหลดต้องมีเฉพาะรายการสินค้าในหมวดหมู่ "เครื่องเขียน" เท่านั้น

Scenario: ส่งออกเมื่อไม่มีสินค้าตรงกับตัวกรอง (Empty Export) 🔧
  Given ผู้จัดการกรองด้วยเงื่อนไขที่ไม่มีสินค้าตรงเลย
  When ผู้จัดการกดปุ่ม "Export CSV"
  Then ระบบดาวน์โหลดไฟล์ .csv ที่มีเฉพาะแถว header โดยไม่มี error
```
> 🔧 เพิ่ม **FR-09** (ด้านล่าง) เพื่อรองรับ AC ชุดนี้อย่างชัดเจน แยกจาก FR-08 ที่เป็นรายงานมูลค่าสต็อก คนละ output กัน และเพิ่มเคส export แบบไม่มีข้อมูล

### AC-07 (US-06 / FR-08) — รายงานมูลค่าสต็อกแยกหมวดหมู่ 🔧
```gherkin
Scenario: แสดงรายงานมูลค่าสต็อกแยกตามหมวดหมู่สำเร็จ
  Given มีสินค้าในหมวดหมู่ "เครื่องเขียน" 3 รายการ และ "อุปกรณ์ไฟฟ้า" 2 รายการ
  When ผู้จัดการเปิดหน้า "รายงานมูลค่าสต็อก"
  Then ระบบแสดงตารางสรุปต่อหมวดหมู่ ประกอบด้วย Total_Items (SUM quantity) และ Total_Valuation (SUM quantity * cost_price) ปัดเศษทศนิยม 2 ตำแหน่ง

Scenario: แสดงรายงานเมื่อไม่มีสินค้าในระบบเลย 🔧
  Given ไม่มีสินค้าใด ๆ ในระบบ
  When ผู้จัดการเปิดหน้า "รายงานมูลค่าสต็อก"
  Then ระบบแสดงข้อความ "ไม่มีข้อมูลสำหรับสร้างรายงาน" แทนตารางเปล่า
```

## 4. In Scope / Out of Scope
**In Scope:**
- การจัดการสต็อกชั่วคราว (In-Memory Stock Management): บันทึกรับเข้า/จ่ายออก พร้อมอัปเดตยอดคงเหลือในหน่วยความจำ
- การจำลองการแจ้งเตือน (Mock Notifications): แจ้งเตือนผ่าน Console log จำลอง Email/SMS
- การสรุปรายงาน (Reporting): รายงานมูลค่าสต็อกแยกตามหมวดหมู่ (US-06)
- การส่งออกข้อมูล (Export): Export รายการสินค้าเป็น CSV (US-05)

**Out of Scope:**
- การส่งข้อความจริง (ไม่เชื่อมต่อ SMTP/SMS Gateway จริง)
- การตรวจสอบสิทธิ์และผู้ใช้งาน (Authentication & Authorization)
- การจัดเก็บข้อมูลถาวร (ไม่มี Database, ข้อมูลหายเมื่อปิดโปรแกรม)
- การรองรับผู้ใช้งานพร้อมกันหลายคน (Multi-user concurrency) — ระบบออกแบบมาสำหรับ single-session เท่านั้น 🔧

> 🔧 เพิ่มข้อยกเว้นเรื่อง concurrency ให้ชัดเจนใน scope เพราะ Design Notes อ้างถึง "Atomic execution" ซึ่งอาจตีความว่าต้องรองรับ concurrent access — ถ้าไม่ต้องรองรับจริง ควรระบุไว้ตรงนี้เพื่อกันการตีความผิด

## 5. Functional Requirements (FR)
| รหัส | ความต้องการ | จาก Story |
|---|---|---|
| FR-01 | ระบบต้องแสดงรายการสินค้าทั้งหมด พร้อม SKU, ชื่อสินค้า, หมวดหมู่, ราคาทุน, ราคาขาย, จำนวนคงเหลือ และสถานะ low-stock (quantity <= threshold) | US-01 |
| FR-02 | ระบบต้องอนุญาตให้เพิ่มสินค้าใหม่ โดยต้องระบุ SKU (unique, case-insensitive), ชื่อ, หมวดหมู่, ราคาทุน (>0), ราคาขาย (>0), หน่วยนับ, จำนวนเริ่มต้น (>=0) และ **threshold (>=0)** 🔧 ให้ครบถ้วน |US-02 |
| FR-03 | ระบบต้องรองรับการบันทึกรายการรับสินค้าเข้า (Stock-in) เพื่อเพิ่มจำนวนคงเหลือ | US-03 |
| FR-04 | ระบบต้องรองรับการบันทึกรายการจ่ายสินค้าออก (Stock-out) เพื่อตัดทอนจำนวนคงเหลือ โดยห้ามให้ยอดคงเหลือติดลบ | US-03 |
| FR-05 | ระบบต้องสร้างข้อความแจ้งเตือนจำลอง (Console, รูปแบบ Email) เมื่อ **quantity <= threshold** 🔧 หลังทำรายการ stock movement | US-03 |
| FR-06 | ระบบต้องสร้างข้อความแจ้งเตือนจำลอง (Console, รูปแบบ SMS) ทุกครั้งที่ทำรายการรับเข้า/ตัดจ่ายสำเร็จ (แยกอิสระจาก FR-05 — อาจเกิดพร้อมกันได้ในธุรกรรมเดียว) 🔧 | US-03 |
| FR-07 | ระบบต้องรองรับการค้นหาสินค้าด้วย SKU หรือชื่อสินค้า แบบ partial match, case-insensitive | US-04 |
| FR-08 | ระบบต้องประมวลผลและแสดงรายงานสรุปมูลค่าสต็อกคงเหลือ จัดกลุ่มตามหมวดหมู่ | US-06 🔧 |
| FR-09 🔧 | ระบบต้องรองรับการ Export รายการสินค้า (ทั้งหมด หรือเฉพาะที่ผ่านการค้นหา/กรอง) เป็นไฟล์ CSV | US-05 |

> 🔧 เพิ่ม **FR-09** ที่หายไปในฉบับเดิม (US-05 ไม่มี FR รองรับ), แก้ FR-08 ให้ map กับ US-06 ที่เพิ่มใหม่, แยกความรับผิดชอบของ FR-05/FR-06 ให้ชัดว่าเป็นคนละ trigger กัน ไม่ใช่ mutually exclusive

## 6. Non-Functional Requirements (NFR)
| รหัส | มิติ | ความต้องการ (ต้องวัดได้) |
|---|---|---|
| NFR-01 | Performance | ระบบต้องประมวลผลและอัปเดตยอดสต็อกในหน่วยความจำได้ภายในไม่เกิน 0.5 วินาทีต่อ 1 รายการ (transaction, search, และ report ใช้เกณฑ์เดียวกันนี้) 🔧 |
| NFR-02 | Accuracy & Integrity | ทุกครั้งที่บันทึกรับ-จ่าย ยอดสต็อกคงเหลือและ Transaction Log ต้องอัปเดตตรงกันทันที ความแม่นยำ 100% |
| NFR-03 | Usability | ไฟล์ CSV ที่ส่งออกต้องเข้ารหัส UTF-8 with BOM 🔧 เพื่อให้เปิดอ่านภาษาไทยบน Excel ได้ถูกต้อง |
| NFR-04 | Maintainability & Extensibility | โค้ดส่วนจำลองการแจ้งเตือนต้องแยกจาก Business Logic หลัก เพื่อรองรับการเชื่อมต่อ SMS/Email Gateway จริงในอนาคต |
| NFR-05 | Reliability & Robustness | ระบบต้องดักจับข้อผิดพลาด (Exception Handling) ป้องกันโปรแกรมหยุดทำงานเมื่อผู้ใช้กรอกข้อมูลผิดประเภท พร้อมแสดงข้อความเตือนที่ตรงกับ Error Schema ในข้อ 8 🔧 |

> 🔧 รวมเกณฑ์ performance ให้เป็นมาตรฐานเดียว, ระบุ UTF-8 with BOM ให้ตรงกับ Design Notes, และผูก NFR-05 เข้ากับ Error Schema ที่มีอยู่แล้วเพื่อให้ "ข้อความเตือนที่ชัดเจน" วัดผลได้จริง (อ้างอิง error code ที่กำหนดไว้)

## 7. Core Domain Entities (Schema)

```
Product:
  sku: string (Unique — case-insensitive, Primary Key)
  name: string (Required)
  category: string (Required)
  cost_price: float (Precision 2 decimal, > 0)
  sell_price: float (Precision 2 decimal, > 0)
  quantity: decimal (Precision 2 decimal — รองรับหน่วยนับที่ไม่ใช่จำนวนเต็ม เช่น เมตร, กก. Default: 0, >= 0)   🔧
  threshold: decimal (Precision 2 decimal, Minimum safety stock level, Required, >= 0)   🔧

Transaction:
  id: uuid (Auto-generated)
  sku: string (Foreign Reference -> Product.sku)
  type: enum [STOCK_IN, STOCK_OUT]
  quantity: decimal (> 0)   🔧
  note: string (Optional)
  timestamp: ISO-8601 string (UTC)   🔧
```
> 🔧 เปลี่ยน `quantity`/`threshold` จาก `integer` เป็น `decimal (2 ตำแหน่ง)` เพราะตัวอย่าง AC ใช้หน่วยนับ "เมตร" ซึ่งเป็นทศนิยมได้ในทางธุรกิจจริง (ขัดกับ schema เดิมที่บังคับ integer) — ถ้าต้องการบังคับ integer จริง ต้องเปลี่ยนตัวอย่างสินค้าในทุก AC ให้เป็นหน่วยนับที่เป็นจำนวนเต็มเท่านั้น (เช่น "ชิ้น") แทน และระบุ timezone ของ timestamp ให้ชัด

## 8. Error & Exception Handling Schema
| Error Code | เงื่อนไข | พฤติกรรม |
|---|---|---|
| DUPLICATE_SKU | เพิ่มสินค้าด้วย SKU ที่มีอยู่แล้ว (case-insensitive) | Reject creation, แสดง "รหัสสินค้านี้มีอยู่ในระบบแล้ว" |
| INSUFFICIENT_STOCK | ตัดจ่ายเกินยอดคงเหลือ | Abort mutation, แสดง "จำนวนคงเหลือไม่เพียงพอสำหรับการตัดจ่าย" |
| INVALID_INPUT_TYPE | ค่าที่กรอกไม่ใช่ตัวเลข/รูปแบบผิด | Return structured error, แสดง "จำนวนต้องเป็นตัวเลขที่มากกว่า 0" |
| NEGATIVE_VALUE | ราคา <= 0 หรือ จำนวน/threshold < 0 🔧 | Reject, แสดง "ค่าต้องไม่ติดลบ และราคาต้องมากกว่า 0" |
| MISSING_REQUIRED_FIELD 🔧 | ไม่กรอก field บังคับ (รวม threshold) | Reject, แสดง "กรุณาระบุ [ชื่อ field]" |
| PRODUCT_NOT_FOUND | อ้างอิง SKU ที่ไม่มีในระบบ | Return 404-style response |

> 🔧 เพิ่ม `NEGATIVE_VALUE` และ `MISSING_REQUIRED_FIELD` ให้ครอบคลุม edge case ที่เพิ่มใน AC-03
